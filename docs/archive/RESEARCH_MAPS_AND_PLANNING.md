# 中国大陆旅行规划、旅游 API 与地图服务调研

调研日期：2026-09-11。范围：当前项目代码、公开项目仓库、平台官方文档与价格页。未注册付费服务、未调用带账号密钥的业务 API，也未部署或运行候选开源项目；功能属于文档核对结果，不能视为实测质量保证。

## 结论与选择

当前项目适合继续增量开发。建议优先参考 TravelPal 的“真实交通数据 + 时间约束求解”，保留本项目已经具备的多人协作、项目隔离、城市资料和导出功能。

- **个人、亲友非商业使用，兼顾开发成本与路线体验：优先高德 JS API + Web 服务 API。** 同一供应商完成地点检索、地图展示、步行/公交/驾车路线，减少坐标和返回格式的适配工作。使用资格、免费期和额度需要与实际账号一致。
- **地图展示费用优先：天地图 JS API，或 Leaflet + 天地图官方底图。** 天地图也有搜索、驾车、公交服务，可以先验证能否覆盖自己的城市和交通需求。其个人地图额度按瓦片请求消耗，不能理解成每天一万次页面访问。
- **商业运营：先核算年度授权，再比较调用单价。** 高德、百度、腾讯的基础年度授权公开标价均为 5 万元；不能用“调用量很小”推导商业使用免费。天地图值得作为低成本候选，但不应推导为任意数据用途、任意调用规模都无条件免费。
- **旅游平台：优先验证飞猪 FlyAI 的搜索接入价值；携程商旅 AI 开放平台更偏企业差旅。** OTA 商品搜索不等同于景点顺序优化、开放时间校验和逐段路网可视化。

以上选型是结合本项目结构作出的工程判断，不是对地图数据准确率的城市级实测排名。价格与配额依据见下文对应官方链接。

## 3. 携程等旅游网站有没有 API

### 携程：有，但要区分三种开放能力

1. **旅游商品与交易开放平台。** 官方公开了门票、玩乐、租车、接送机等内容及订单对接，面向供应商和分销商。部分接口的方向是“携程调用供应商”，并不是开发者用一个 Key 就能搜索携程全部商品。接入一般涉及合作身份、沙箱和联调。依据：[平台上线公告](https://ttdopen.ctrip.com/apiplatform/help-detail.do?no=88)、[供应商接入说明](https://ttdstp.ctrip.com/apiplatform/document/channelin.do)、[新订接口的调用方向](https://ttdstp.ctrip.com/apiplatform/api/neworderplaced.do)。
2. **商旅业务接口。** [携程商旅开发者平台](https://openapi.ctripbiz.com/)包含企业差旅系统集成能力，适合审批、人事、差旅服务等业务，不是个人游记或攻略数据下载接口。
3. **商旅 AI/MCP 开放平台。** 携程商旅在 2026-04-20 的官方介绍中确认，向企业客户和生态伙伴开放信息查询、机酒火车资源推荐等 AI 能力，并设标准、高级、定制层。文章提及智能行程规划，但本次未找到个人可自助使用的“多日景点约束排程 REST API”、公开统一报价或个人免费额度。依据：[携程商旅官方说明](https://ct.ctrip.com/thinktanks/235566117077549)。

因此，不能说“携程没有 API”，也不能把其企业 AI 产品宣传当作本项目马上可用的公共排程接口。

### 飞猪：FlyAI 比传统供应链 API 更值得先验证

飞猪传统开放平台主要提供商家产品、价格库存和订单对接：[官方业务介绍](https://developer.alibaba.com/docs/doc.htm?articleId=106550&docType=1&treeId=79)。

[飞猪 AI 开放平台](https://flyai.open.fliggy.com/)与[能力说明](https://flyai.open.fliggy.com/docs/overview)则聚焦自然语言全域搜索、酒店、机票和 POI 搜索，比较适合给当前 AI 助手增加真实旅游资源。

- 官方 [FlyAI 仓库](https://github.com/alibaba-flyai/flyai-skill)为 MIT，提供 CLI/Skill，并返回结构化搜索结果和预订链接。当前 README 还列出火车搜索；网页文档与 CLI 命令有版本差异，接入时应固定版本核对。
- [快速开始](https://flyai.open.fliggy.com/docs/quickstart)建议申请正式 API Key，以获得更多调用次数和稳定服务；仓库提及可无 Key 起步，但这不等于生产环境无限免费。本次未查到公开统一计价表或可用于预算的明确额度。
- [官方 FAQ](https://flyai.open.fliggy.com/docs/faq)说明部分商品不返回价格，应通过 `jumpUrl` 到详情页查看。这类结果不能被当作实时、完整的本地价格库。
- 本项目可先验证“景点/酒店/交通搜索 → 卡片预览 → 外链预订”，不要把语义搜索结果直接当作满足全部时间约束的行程。

### 同程/艺龙、美团

| 平台 | 官方公开能力 | 对当前项目的价值 |

## 5. 低成本落地方案

### A. 推荐的个人非商业版本：高德一体化

前端使用高德 JS API 展示编号地点、按日配色路线和信息卡；后端通过 Web 服务 API 查询真实 POI 与交通方案。高德[路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)明确提供多种交通方式；实现时按具体接口请求耗时、费用和道路折线等字段，例如驾车的 `show_fields=cost,polyline`，不要只画起终点直线。

成本示例是工程假设，不是平台报价：每次旅行处理 30 次搜索、20 次路线请求、20 次地图初始化；每月 100 次旅行，对应搜索 3,000 次、路线 2,000 次、地图初始化 2,000 次。若符合高德个人非商业免费期、没有其他应用共同耗用额度，这些用量低于上述免费额。

若全部按公开基础单价折算，调用消耗价值约为：

$$
(3000+2000)\times\frac{30}{10000}+2000\times\frac{3}{10000}=15.6\text{ 元/月}
$$

该数值**不等于实际最低付款额**：未计流量包起购、有效期、其他调用、并发升级、年度授权、服务器和模型费用。商业用途仍需另算授权费用；其金额会远大于这个小用量示例的调用成本。

### B. 展示费用优先版本：天地图 + 轻量前端

可选天地图自己的 JS API，或者 [Leaflet](https://leafletjs.com/) 加官方带 Key 的底图。Leaflet 提供标记、弹窗和折线，无需 React/Vue，也不自带中国地图或路线数据。

第一版可以做到：城市景点落点、每日编号、点击列表定位地图、每天路线分色；没有查到真实道路的部分显示为“行程顺序示意”虚线，不能给用户制造已验证交通路线的印象。

如同时需要路线耗时，应先用天地图搜索和驾车/公交服务测试目标城市。不能为了节省底图费，默认把高德 POI/路线数据混到天地图上：这还涉及数据展示授权与坐标转换，未核实前不作为默认架构。

### C. 不建议作为第一版的路径

- **自建 OSM + OSRM/GraphHopper 全套国内地图与路网**：节省供应商调用费的同时增加数据更新、服务器、路网质量和地图发布工作，无法自然补齐国内公交、地铁和景区入口。当前项目规模下工程成本偏高；此项为工程判断。
- **直接依赖公共 OSM 瓦片作免费生产 CDN**：OSM 数据开放不等于公共瓦片服务无限用。其官方政策明确限定使用行为且不提供 SLA。[OSMF 瓦片政策](https://operations.osmfoundation.org/policies/tiles/)
- **免 Key 地图瓦片、逆向 OTA 接口、购买不明来源共享 Key**：不作为可维护的成本方案；正式接入应选择官方接口和对应账号权益。

## 6. “合理行程”应如何实现

推荐数据流：需求与候选景点 → POI 消歧与入口确认 → 交通耗时 → 本地约束校验/优化 → AI 整理说明 → 用户预览 → 地图与时间线。

### 地点层

新增统一地点对象，适用于景点、餐厅、酒店、车站和机场。建议字段包括本项目地点 ID、名称、城市行政码、供应商、供应商 POI ID、坐标系、经纬度、入口信息、确认状态、来源和查询时间。供应商字段是否持久化以及保留多久须按授权确定；用户原创资料与外部数据分开处理。

同名地点列出候选让用户确认；“故宫”“某景区”“某餐厅连锁店”不能不加核对就选第一个结果。大型景区优先使用游客入口/导航点，避免以景区中心当步行终点。

高德采用 GCJ-02；百度接口提供 BD-09 等坐标选项；天地图图层应按具体服务的 CRS 处理。无论选哪家，始终保留坐标系标记，不能把所有 `lat/lng` 当作可直接混用。依据：[高德坐标说明](https://lbs.amap.com/api/javascript-api-v2/guide/abc/basetype)、[百度地点检索坐标参数](https://lbs.baidu.com/docs/webapi?title=placev3%2Fguide%2Fwebservice-placeapiV3%2FinterfaceDocumentV3)。

### 时间和路线层

每个活动增加 `stay_minutes`、开始/结束时间、允许访问的时间窗、是否锁定预约；每两个活动之间增加一段交通，包含方式、距离、预计耗时、出发时刻、路线状态和来源时间。开放时间缺失时标为未知，不能让模型编造后当成硬约束。

最基本的校验为：

$$
\text{下一项开始时间}\geq\text{上一项结束时间}+\text{交通耗时}+\text{缓冲时间}
$$

还要分别考虑酒店起终点、用餐休息、最晚入园、预约时间、每日步行上限。公交/驾车耗时随出发时间变化，跨城交通需加车站/机场接驳与候车缓冲；地图路线 API 不能代替具体车次、航班和座位查询。

先实现固定顺序的可行性校验，再做优化。少量景点可用分片区、贪心插入、2-opt 和逐项时间检查；复杂多日问题再评估 OR-Tools。优化目标应优先满足已预约和必去活动，再减少通勤、控制步行和调整可选景点，而不是一味追求最短距离。无解时明确列出冲突并建议删减，不强行给出“可行”结果。

### 可视化层

- 地图与每日行程列表双向联动；当前日期突出显示，其他日期可开关。
- 每站按顺序编号，交通段显示方式、耗时和距离。
- 公交拆出步行接驳及乘车段，跨城线与城市内部路线区别显示。
- 真实路线用实线；顺序示意和查询失败用虚线及文字标记。
- 修改排序后更新相邻路段，比较优化前后的总通勤时间；不随 5 秒协作轮询重复发起算路。
- 手机使用列表/地图切换或可收起地图，保留现有地铁图与跳转导航作为补充。

### 控制成本与数据使用

地图按需加载；复用一个地图实例；搜索输入防抖、限制候选数量；先对计划内地点算路，只重算改变的路段；设置项目和部署级调用预算及限流。20 个候选点全量有向两两查询为 380 个组合，若每次 AI 重排都重新获取，会远高于只验证相邻路段。

不预设“永久缓存 POI/路网数据”来省钱。高德现行协议对直接存储、缓存、抓取服务内部内容有约束，百度也限制相关内容的复制与数据库化。缓存字段、期限、跨项目共享及地图导出权限应按具体产品规则或书面授权配置；无明确许可时，不把服务商结果写进现有全局景点缓存。依据：[高德服务协议](https://lbs.amap.com/pages/terms/)、[百度服务条款](https://lbs.baidu.com/docs/pcsa?title=law%2Fopen%2Flaw)。

## 7. 建议的实施顺序与验证范围

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 1. 地点与地图 | 地点消歧、坐标来源、当前城市/每日落点、列表联动 | 同名景点、分店、大景区入口、手机操作、无 Key 时保留现有功能 |
| 2. 真实路线 | 步行/公交/驾车、逐段折线与交通卡片、查询失败状态 | 不能用驾车时间替代步行；跨江、单行道、末班车、景区入口分别核对 |
| 3. 约束排程 | 停留时长、预约锁定、每日可用时间、超时冲突、优化预览 | 有解/无解都能解释；已预约项目不被擅自移动；沿用协作版本检查 |
| 4. OTA 搜索 | 先验证 FlyAI 的景点/酒店/机票/火车搜索和跳转 | 身份与额度、结果覆盖、缺失价格、跳转目标、API/CLI 版本稳定性 |

建议以当前已有资料较多的上海为首个验证城市，再增加杭州、北京或南京。用一组固定的真实 POI 对分别测试：短距步行、跨江、公交换乘、大型景区入口、郊区景点、车站接驳。记录成功率、候选命中、路线耗时与实际 App 差异、单日调用量和移动端地图操作感受，再决定是否需要第二供应商。

当前调研没有修改业务代码、项目配置、数据库或现有未提交改动；仅新增本文档。
